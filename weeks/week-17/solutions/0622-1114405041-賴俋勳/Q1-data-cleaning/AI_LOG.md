# AI_LOG.md - Q1 資料清理 (Data Cleaning)

## 我問 AI 什麼

「請幫我用 unittest 寫 data_cleaning(input_data) 的參數化測試，至少 3 個案例，含邊界情況。我的參數 D=3，但測試應該通用。」

---

## AI 給了什麼

AI 提供了：
- 5 個測試用例（超過要求的 3 個）
- 包含邊界情況：空陣列、單元素、全重複、無重複、基本清理
- 使用參數化接口 `data_cleaning(input_data)` 而不是 stdin/stdout
- 但初版沒有提及 API 的重要性

---

## 我改了什麼

### 改進1：API 不匹配的發現與修正
**原問題**：
- 測試期望 `data_cleaning(input_data)` —— 參數化接口，返回字符串
- 原實作是 `data_cleaning()` —— 讀取 stdin，print 到 stdout

**我的判斷**：
這是致命的 API 不匹配。SOP 要求「紅燈 → 綠燈」才算數，但如果 API 不符，測試永遠無法通過。

**我的改法**：
1. 要求 AI 提供正確的參數化實作
2. 修改 `data_cleaning.py` 改為：`def data_cleaning(input_data)` 返回字符串
3. 移除 stdin/stdout 讀取邏輯

### 改進2：測試與實作分離
**原問題**：
測試文件中包含實作代碼 —— 這違反了 SOP 的「紅燈 → 綠燈」要求

**我的判斷**：
- 如果實作在測試文件裡，測試一開始就會是綠燈
- 無法驗證真正的「紅燈→綠燈」過程
- 這在期末考會直接扣流程分

**我的改法**：
1. 從 `test_data_cleaning.py` 刪除所有實作代碼
2. 添加 `from data_cleaning import data_cleaning` 導入語句
3. 確保測試文件 **只** 包含測試邏輯

### 改進3：邊界情況的完整性
**原問題**：
需要確認邊界情況是否真的能觸發「紅燈」

**我的判斷**：
- `test_empty_list`: 空陣列應返回 ""
- `test_single_element`: 單個元素應返回該元素
- 這些邊界情況對於驗證實作邏輯至關重要

**我的改法**：
保留所有 5 個測試用例，確保邊界覆蓋完整

## 學習收穫

1. **API 設計的重要性**：參數化接口比 stdin/stdout 更易測試
2. **測試與實作的嚴格分離**：SOP 不只是流程，也是設計原則
3. **邊界情況必須主動測試**：不是加起來就好，要真的能失敗再成功
