easy.py 程式優化與偵錯說明

一、這支程式在做什麼

這支程式使用動態規劃 DP 加上 bitmask 來計算答案。

輸入會有多筆測資。
每筆測資有 n 列、m 欄。
格子中的 1 表示可以使用，0 表示不能使用。

程式會判斷所有可用格是否能用合法連線方式組合，
並計算總共有幾種合法方法。

答案需要對 1000000007 取餘數。


二、我做了哪些優化

【1】保留 normalize_row()，讓輸入格式更穩定

原本程式可以處理：

1 0 1

也可以處理：

101

這個功能是好的，所以我保留下來。

這樣不管題目測資是空白分隔，還是數字黏在一起，
程式都可以正確讀取。


【2】將 transitions 改名成 get_transitions

原本函式名稱是 transitions。

我改成 get_transitions，
讓函式名稱更清楚。

意思是：
取得某一列在某個 up_mask 狀態下，所有可能的 down_mask 轉移。


【3】保留 lru_cache，加速重複狀態

這題會一直重複計算：

row_mask
up_mask
m

相同時的轉移結果。

所以使用：

@lru_cache(maxsize=None)

可以把算過的結果記住。
下次遇到相同狀態時，不需要重新 DFS。

這是這支程式最重要的效能優化之一。


【4】使用 bitmask 壓縮狀態

原本每一列是 list，例如：

[1, 0, 1]

優化後會轉成 bitmask。

例如：
第 0 欄可用，第 2 欄可用，
就會變成二進位：

101

這樣可以用位元運算快速判斷某格是否可用。

例如：

(row_mask >> col) & 1

可以判斷第 col 欄是不是可用格。


【5】加強變數命名

原本的變數有：

result
need
new_dp

這些可以用，但我做了一些調整：

cell_is_empty 改成 cell_is_available
new_dp 改成 next_dp
ways_so_far 改成 ways
count_transition 改成 transition_count

這樣語意比較清楚。

尤其是 cell_is_empty 這個名字容易誤會，
因為這裡的 1 其實代表可用格，不一定是「空」。
所以改成 cell_is_available 比較準確。


【6】保留 DFS 產生轉移

每一列的轉移使用 DFS 處理。

DFS 會從第 0 欄一路處理到第 m - 1 欄。
每個格子會根據：

左邊是否有邊 left_edge
上面是否有邊 up_edge
目前格子是否可用

來決定能不能往右或往下接邊。


【7】加入更詳細的繁體中文註解

這份程式的邏輯比較難，
所以我補上較詳細的繁體中文註解。

註解包含：

1. row_mask 是什麼
2. up_mask 是什麼
3. down_mask 是什麼
4. left_edge 是什麼
5. 為什麼可用格度數要剛好是 2
6. 為什麼最後 dp.get(0, 0) 才是答案

這樣比較適合作業繳交，也比較容易被老師看懂。


三、偵錯後確認

【1】輸入讀取正常

程式可以正確讀取：

1 0 1

也可以正確讀取：

101

所以輸入格式比較不容易出錯。


【2】可以跳過測資前空白行

main() 裡面有：

while index < len(lines) and lines[index].strip() == "":
    index += 1

所以測資之間有空白行也不會影響。


【3】障礙格處理正確

如果目前格子是 0，
代表不能使用。

障礙格不能有左邊來的邊，也不能有上面來的邊。

所以只有在：

left_edge == 0
up_edge == 0

時，才能繼續往下一格處理。


【4】可用格度數限制正確

可用格必須剛好有 2 條邊。

所以程式使用：

need = 2 - left_edge - up_edge

如果 need 是 0：
代表已經有兩條邊，不可以再接右邊或下面。

如果 need 是 1：
代表還需要一條邊，可以選擇往右或往下。

如果 need 是 2：
代表還需要兩條邊，必須同時往右和往下。


【5】右邊邊界檢查正確

如果要往右接邊，必須確認右邊有格子，
而且右邊格子也是可用格。

所以程式使用：

right_available = col + 1 < m and ((row_mask >> (col + 1)) & 1) == 1

這樣可以避免右邊超出範圍。


【6】最後狀態正確

所有列都處理完後，不能還有邊往下一列接出去。

所以答案是：

dp.get(0, 0)

也就是 down_mask 必須是 0。


四、這次優化的重點

1. 程式結構更清楚
2. 變數名稱更好懂
3. 保留 lru_cache 加速
4. 保留 bitmask 降低狀態空間
5. 增加詳細繁體中文註解
6. 加強輸入處理穩定性
7. 使用 sys.stdout.write 精準輸出


五、總結

這次優化主要是針對可讀性、穩定性與效能。

原本程式的演算法方向是正確的，
使用的是「逐列 DP + bitmask + DFS 產生轉移」。

我做的事情是：

1. 整理函式名稱
2. 改善變數命名
3. 增加詳細註解
4. 保留快取機制
5. 加強輸入與輸出處理

優化後的程式比較容易理解，
也比較適合拿去交作業或之後自己複習。
